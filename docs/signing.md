# Signing releases

[← back to the README](../README.md)

## What signing is for

When you publish a jar to Clojars, anyone who depends on your library downloads those
bytes and runs them. They are trusting a chain: that Clojars stored what you uploaded,
that the CDN in front of it served what Clojars stored, and that nobody with access to
any of that swapped the file along the way. None of those links are things your
consumers can check.

A signature gives them something they *can* check. Before publishing, we run the jar
through GPG using a private key only we hold. GPG produces a short block of text — a
**detached signature** — that could only have been generated by that key over exactly
those bytes. We publish that block next to the jar. Anyone with the matching *public*
key can then verify two things at once: the bytes came from us, and they have not
changed by a single byte since we signed them.

"Detached" is the important word. GPG does not modify the jar; it writes a second file
next to it:

```
bucket-2.14.0.jar        <- the artifact
bucket-2.14.0.jar.asc    <- the signature over it
```

That has a practical consequence that trips people up: **because the signature is a
separate file, it has to be uploaded separately.** Signing locally accomplishes nothing
on its own. See [custom builds](custom-builds.md) if you write your own publish step.

## What signing does not prove

A signature proves *who produced the bytes*. It says nothing about *where they came
from* — which repository, which commit, which build. A key can sign anything, including a
jar built from uncommitted code on a laptop.

That second question is what the **attestation** answers. GitHub's
`attest-build-provenance` action uses a short-lived OIDC token, issued to the workflow
run itself, to state: this artifact was built by this repository, in this workflow, at
this commit. That statement is not forgeable by someone holding the signing key, because
it is not produced by the signing key.

The two checks are complementary and neither replaces the other:

| Check | Answers | Broken by |
|---|---|---|
| GPG signature | "Did the key holder produce these bytes?" | A stolen private key |
| Attestation | "Did this repo and commit produce these bytes?" | A compromised workflow |

Both are described from the consumer's side in
[verifying a release](verifying-a-release.md).

## Turning it on

Signing is **opt-in**, and off unless you ask for it:

```clojure
:exec-args {:group       "com.example"
            :lib-name    "mylib"
            :repo        "example/mylib"
            :ci-workflow ["test.yml"]
            :license-url "https://github.com/example/mylib/blob/master/LICENSE"
            :sign        true}    ;; <- this
```

With `:sign true`, `deploy` requires `GPG_PRIVATE_KEY` and `GPG_PASSPHRASE` on the
`clojars` environment, and it checks for them **before it builds anything** — a missing
key costs you one line of output, not a failed publish. It then signs the jar, the pom,
and (if `:sbom` is on) the SBOM, uploads each `.asc` alongside its file, and signs the
release tag with the same key.

Without `:sign`, the release publishes unsigned and says so in the log. That is a weaker
release, but it is a working one, which matters when a repo bumps its pinned `:git/sha`
for an unrelated fix.

## Generating the key

One key per organization is the simplest arrangement that works: someone verifying any
of your artifacts imports one key rather than one per library. Per-repository keys work
too — the library reads whatever key is in the environment and does not care how many
exist.

Do this once, on a machine that is not a CI runner.

The key has two parts, and the split matters. The **primary key** gets `cert` usage
only: its job is to certify subkeys, and it is the thing whose loss would be
unrecoverable, so it never leaves the offline machine. A dedicated **signing subkey**
sits under it, and that is the part CI gets. If CI is ever compromised, you revoke the
subkey and issue a new one; the identity survives.

```bash
gpg --quick-generate-key "<YOUR_ORG> Release <releases@example.com>" ed25519 cert never
gpg --quick-add-key <FINGERPRINT> ed25519 sign never
gpg --send-keys <FINGERPRINT>                          # publish the public half
```

An encryption subkey is unrelated to signing and never used here. Skip it unless
something else in your organization needs one:

```bash
gpg --quick-add-key <FINGERPRINT> cv25519 encr never   # optional
```

Confirm the signing subkey exists before exporting anything. The listing marks its
capability `[S]`:

```bash
gpg --list-secret-keys --with-subkey-fingerprints
# sec   ed25519 ... [C]                      <- the primary, cert-only
#       <FINGERPRINT>
# ssb   ed25519 ... [S]                      <- the signing subkey; note its id
#       <SIGNING_SUBKEY_ID>
```

## Exporting the subkey for CI

Export **only that signing subkey**. The trailing `!` is what pins the export to that
exact subkey rather than every subkey on the key:

```bash
gpg --batch --pinentry-mode loopback --passphrase '<PASSPHRASE>' \
    --armor --export-secret-subkeys <SIGNING_SUBKEY_ID>! > release-subkey.asc
```

**`--batch --pinentry-mode loopback --passphrase` is not optional here, and leaving it
off fails in a way that looks like success.** This is worth understanding, because the
failure surfaces much later.

Without those flags, gpg cannot prompt for the passphrase when there is no controlling
terminal, so it exits 2 with:

```
gpg: key <KEYGRIP>: error receiving key from agent: Inappropriate ioctl for device - skipped
```

But the shell redirect has *already created* `release-subkey.asc`. What lands there is a
complete, plausible-looking armored block — roughly 450 bytes against the ~1000 a real
export produces — containing the primary's `gnu-dummy` stub, the uid, and its binding
signature, and **no secret subkey at all**. `gpg --import` then reports
`Total number processed: 1`, `imported: 1`, `secret keys read: 1`, and exits 0. Nothing
complains until something tries to sign, which fails with `no default secret key: No
secret key` — in production, that means *inside a release*, after the jar is built.

So verify the export before it becomes a secret. Check the packets, not the file size:

```bash
gpg --list-packets release-subkey.asc | grep -E ':secret (sub )?key packet:|skey\['
```

A correct export shows both of these:

```
:secret key packet:            <- the primary, as a stub (see below)
:secret sub key packet:        <- the signing subkey
	skey[2]: [v4 protected]      <- its encrypted secret material, present
```

A broken one shows only `:secret key packet:` and no `skey[` line anywhere. **The `skey`
line is the actual check** — it is the secret material, and its absence is what makes
the file useless. (`gpg --import` also prints `secret keys imported: 1` for a good export
and omits that line for a broken one, which is a quicker signal if you have the import
output in front of you.)

The primary's secret material is not in either file. Both show its
`:secret key packet:` as a `gnu-dummy` stub with no `skey` of its own. That is
`--export-secret-subkeys` doing what it promises, and it is why importing this file gives
CI a key that can sign releases but cannot certify new subkeys.

### Passphrase hygiene for that one command

A passphrase in `--passphrase` is visible in a process listing. The release library never
does this — it always feeds gpg on stdin — but it is a defensible tradeoff for a one-off
command on an offline machine. If you would rather not, `--passphrase-fd 0` keeps it out
of the process listing:

```bash
printf '%s' '<PASSPHRASE>' | gpg --batch --pinentry-mode loopback --passphrase-fd 0 \
    --armor --export-secret-subkeys <SIGNING_SUBKEY_ID>! > release-subkey.asc
```

Neither form keeps it out of your **shell history** — the pipeline above is itself a
history line containing the passphrase. Prefix whichever you use with a space
(`HISTCONTROL=ignorespace` in bash, `setopt HIST_IGNORE_SPACE` in zsh), or delete the
entry afterwards.

## Installing the secrets

Add the contents of `release-subkey.asc` as `GPG_PRIVATE_KEY` and the passphrase as
`GPG_PASSPHRASE`, both on the **`clojars` environment** of each repository — never at
repository level, where every workflow in the repo could read them. See
[releasing](releasing.md#the-clojars-environment) for how that environment is set up and
how to check the secrets landed in the right place.

## Rotation

Generate a new subkey, publish it, update the two secrets in each repository, and **leave
the old public key on the keyservers.** Artifacts already published stay verifiable
against the key that signed them; revoking it would invalidate signatures on releases
that were never compromised.
